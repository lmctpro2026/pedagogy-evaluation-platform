03Demographic collection — R1

Participant flow

On completing the survey the participant is asked “Are you happy to provide demographic information?” Selecting Yes opens a dedicated page; selecting No thanks proceeds directly to their results. Both paths reach the results page in a single action, so the optional step never obstructs the participant.

Fields collected

FieldOptions presented
Age groupUnder 25 · 25–34 · 35–44 · 45–54 · 55–64 · 65 or over · Prefer not to say
GenderMale · Female · Other, with a free-text description limited to 60 characters · Prefer not to say
Academic levelLevel A (Associate Lecturer) · Level B (Lecturer) · Level C (Senior Lecturer) · Level D (Associate Professor) · Level E (Professor) · Other · Prefer not to say

Data model

  • A new demographics table stores one record per survey session, joined to the score record by session identifier. This satisfies the requirement that the information be linked to the same survey response.
  • Declines are recorded explicitly. Without this the opt-in rate could not be reported, as a participant who declined would be indistinguishable from one never asked.
  • Records are write-once. No update or delete permission is granted, so possession of a session identifier does not permit a record to be altered.
  • Permitted values are enforced by database constraints as well as by the interface, so malformed data cannot be introduced by bypassing the form.
Ethical considerations

Every question offers a “Prefer not to say” option, so requiring an explicit selection never compels disclosure. Responses are attached to the assessment record rather than to a participant's name, and participants using the anonymous access route may contribute demographic data without creating an account.

Framework category results

The existing category bar chart is now accompanied by a numerical table reporting the count of responses, mean, median, lowest and highest value for each of the four framework categories — Teaching Practice, Pedagogical Development, Technology Adoption and Techno-Pedagogical Practice — together with an overall composite. Both the chart and the table are computed from the same set of completed sessions, so the two presentations cannot disagree.

Demographic summaries

Three bar charts present the distribution of age group, gender and academic level across participants who opted in. Categories with no responses are omitted so that small samples remain legible. Demographic data is also surfaced in the participant table, in individual participant records, and as four additional columns in the exported data file for subsequent analysis.

Defect identified during implementation

Assessment sessions that could not be matched to a participant record were being excluded from the dashboard entirely. These are now reported as unattached sessions. Had this gone uncorrected, the participant count required by R2 would have under-reported the true total.

05Validation and error handling — R3

Two points of validation

  • At each question. Attempting to advance without selecting a response displays an explicit message — “Please select a response before continuing — every question is required.” — in place of the previous behaviour, which silently disabled the button and gave the participant no explanation. The message clears as soon as a response is selected.
  • At submission. The final question leads to a review screen listing all twenty responses grouped by framework category. Attempting to submit while incomplete is refused, and the resulting message identifies the specific unanswered question numbers and links directly to the first of them.

Results saved only on completion

A single point in the code governs this. No score is calculated, stored, or transmitted until all twenty questions hold a valid response. This was confirmed by attempting an incomplete submission and verifying that neither the local record nor the database contained any result.

Design decision

Because each question must be answered before the participant can advance, the submission step could not otherwise be reached in an incomplete state, making R3 impossible to demonstrate. A Review answers control was therefore added to the progress bar, allowing the review screen to be opened at any point. This both makes the rule testable and lets participants check their progress before submitting.

06Quality assurance

Four defects were identified during a structured review of the new code and resolved before the build was passed to testing.

1  Save failures were reported to the participant as successes

Data integrity · js/assessment.js

The database client reports failures through a returned value rather than by raising an exception, and that value was not being examined. A rejected write — whether from a permissions rule, a constraint violation, or loss of connectivity — passed unnoticed, and the participant was informed their results had been saved. Both the score update and the response insertion are now checked, and the completion screen reports the true outcome in either case.

2  Navigating away could cancel the save in progress

Data loss · js/questionnaire.js

The save was performed in the background while the completion screen already offered controls that navigate to another page, so a prompt selection could terminate the request before it completed. Those controls are now held, with a visible progress indicator, until the write has settled, subject to a six-second limit so that a participant is never detained by an unresponsive connection.

3  Validation messages could attach to the wrong question

Correctness · js/questionnaire.js

Two question panels exist briefly during the transition animation. An error message could therefore be attached to the panel leaving the screen rather than the one presented to the participant. All references are now bound to the active panel.

4  Returning from the review screen moved the participant to the final question

Usability · js/questionnaire.js

Opening the review screen partway through the survey and returning placed the participant at question twenty rather than at the question they had left. The original position is now preserved.

Formal testing

A written test script, SPRINT3_TEST_PLAN.md, has been prepared for the tester. Sections 1 to 5 correspond to the five verification items specified under R4; sections 6 and 7 extend coverage to the dashboard and to regression checks on existing functionality. Each step states the action and the expected result, with explicit pass criteria.

Limitation of developer verification

The development environment used for this verification had no network route to the hosted database, so the round trip to the live database could not be exercised. Client-side behaviour is verified; confirming that a demographic record is written to the database is covered by step 5.1.9 of the test script and is carried out during the testing phase.
